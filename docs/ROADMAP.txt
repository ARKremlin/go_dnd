ТЗ — go_dnd (D&D 5e)

1. Общие сведения и архитектура системы
Проект представляет собой бэкенд-сервис для проведения пошаговых боёв по правилам D&D 5e без графического интерфейса (Headless VTT).

Технологический стек:
- Основной язык: Go (Clean Architecture, REST API, slog, internal Event Bus на каналах chan Event).
- PostgreSQL: единственный источник истины (Single Source of Truth, SSOT) для всех персистентных данных, включая текущее состояние боя.
- Redis: буфер событий боя для polling. Кэш очереди инициативы и текущего раунда отложен (TD-24).
- Хранилище медиа: MinIO / S3 (аватарки персонажей и токены монстров). Адаптер — internal/pkg/storage. В БД хранятся только URL.
- Клиентские интерфейсы:
  - Мастер (DM): Swagger UI (интерактивная документация REST API) и Postman-коллекция в репозитории. События боя получает через polling (периодический GET с указанием последнего полученного события).
  - Игроки (Players): Telegram Bot API (библиотека github.com/go-telegram/bot, управление через инлайн-кнопки).

Слои зависят только внутрь:

transport (REST, Telegram)  ->  usecase  ->  domain  <-  repository (PostgreSQL)

domain: сущности, доменные ошибки, интерфейсы репозиториев.
usecase: бизнес-логика, знает только интерфейсы.
repository/postgres: реализация интерфейсов на pgx.
transport/rest, transport/telegram: входящие запросы, преобразование ошибок в ответы.

2. Аутентификация, роли и схема данных

2.1. Модель пользователей
Единая таблица users с гибкой структурой полей в зависимости от роли (role: player | dm):
- Игрок (Player): заполняются telegram_id (BIGINT, unique) и telegram_username (TEXT, unique, nullable). Поле password_hash — NULL. Поле username — NULL.
- Мастер (DM): заполняются username и password_hash. Поля telegram_id и telegram_username — NULL. Авторизация через REST API (/login) с выдачей JWT-токена.

2.2. Схема базы данных (PostgreSQL)

users:
- id UUID, PK, DEFAULT uuid_generate_v4()
- telegram_id BIGINT, UNIQUE (частичный), NULLABLE
- telegram_username TEXT, UNIQUE (частичный), NULLABLE
- username TEXT, UNIQUE (частичный), NULLABLE
- password_hash TEXT, NULLABLE
- role TEXT, NOT NULL, CHECK IN ('player', 'dm')
- created_at TIMESTAMPTZ, NOT NULL, DEFAULT NOW()

CHECK-констрейнт users_role_consistency:
- role = 'player' → telegram_id IS NOT NULL AND password_hash IS NULL AND username IS NULL
- role = 'dm' → telegram_id IS NULL AND telegram_username IS NULL AND username IS NOT NULL AND password_hash IS NOT NULL

Частичные индексы: по telegram_id, telegram_username, username (там, где значение не NULL).

tables:
- id UUID, PK
- dm_id UUID, FK → users.id ON DELETE CASCADE
- name VARCHAR(128), NOT NULL
- created_at TIMESTAMPTZ, NOT NULL
Индекс idx_tables_dm_id.

table_members:
- id UUID, PK
- table_id UUID, FK → tables.id ON DELETE CASCADE
- player_id UUID, FK → users.id ON DELETE CASCADE
- status VARCHAR(16), NOT NULL, DEFAULT 'pending', CHECK IN ('pending', 'accepted', 'declined')
- created_at TIMESTAMPTZ, NOT NULL
UNIQUE (table_id, player_id). Индексы по table_id и player_id.

characters:
- id UUID, PK
- player_id UUID, FK → users.id ON DELETE CASCADE, UNIQUE
- name VARCHAR(64)
- race, class — идентификаторы из JSON-правил
- level INT, DEFAULT 1, CHECK (level >= 1)
- xp INT, DEFAULT 0, CHECK (xp >= 0)
- max_hp INT, CHECK (max_hp > 0)
- current_hp INT, CHECK (current_hp >= 0 AND current_hp <= max_hp)
- ac INT
- stats_json JSONB, NOT NULL
- actions_json JSONB, NOT NULL, DEFAULT '[]'
- bonus_actions_json JSONB, NOT NULL, DEFAULT '[]'
- avatar_url VARCHAR(512), NULLABLE
- created_at TIMESTAMPTZ, NOT NULL

bestiary_templates:
- id UUID, PK
- dm_id UUID, FK → users.id ON DELETE CASCADE
- name VARCHAR(128)
- ac INT
- max_hp INT, CHECK (max_hp > 0)
- xp_reward INT, NOT NULL, DEFAULT 0, CHECK (xp_reward >= 0)
- stats_json, actions_json, bonus_actions_json JSONB
- avatar_url VARCHAR(512), NULLABLE
- created_at TIMESTAMPTZ, NOT NULL
Индекс idx_bestiary_dm_id.

encounters:
- id UUID, PK
- table_id UUID, FK → tables.id ON DELETE CASCADE
- status VARCHAR(16), NOT NULL, DEFAULT 'preparing', CHECK IN ('preparing', 'active', 'finished')
- round INT, NOT NULL, DEFAULT 0
- current_turn INT, NOT NULL, DEFAULT 0
- created_at TIMESTAMPTZ, NOT NULL
- finished_at TIMESTAMPTZ, NULLABLE
Индекс по table_id. Частичный уникальный индекс ON encounters(table_id) WHERE status IN ('preparing', 'active') — не больше одного незавершённого боя на стол.

encounter_entities:
- id UUID, PK
- encounter_id UUID, FK → encounters.id ON DELETE CASCADE
- entity_type CHECK IN ('player', 'monster')
- source_id UUID (characters.id для игрока, bestiary_templates.id для монстра)
- display_name VARCHAR(128)
- current_hp, max_hp, ac INT
- stats_json, actions_json, bonus_actions_json JSONB, NOT NULL
- xp_reward INT, NOT NULL, DEFAULT 0
- status VARCHAR(16), NOT NULL, DEFAULT 'active', CHECK IN ('active', 'unconscious', 'dead')
- initiative_score INT, NULLABLE
- turn_position INT, NULLABLE
- action_used BOOL, NOT NULL, DEFAULT FALSE
- bonus_action_used BOOL, NOT NULL, DEFAULT FALSE
UNIQUE (encounter_id, turn_position). Индекс по encounter_id.

dice_rolls_log:
- id UUID, PK
- encounter_id UUID, FK → encounters.id ON DELETE CASCADE
- actor_name, action_name, roll_type CHECK IN ('initiative', 'attack', 'damage'), dice_formula
- result_detail JSONB
- created_at TIMESTAMPTZ, NOT NULL
Индекс (encounter_id, created_at).

2.3. Файловое хранилище (MinIO / S3)
- Валидация: строгий фильтр расширений .png, .jpg, .jpeg и типа по содержимому (http.DetectContentType).
- Ограничение: максимальный размер файла — 5 МБ.
- Хранение: файлы — в MinIO. В БД — только avatar_url.

3. Движок правил и игровой процесс

3.1. Конфигурация правил (JSON Rules Engine)
Все игровые константы вынесены в JSON-файлы в configs/rules/:
- races.json: Человек, Эльф, Дварф + stat_modifiers.
- classes.json: Воин, Жрец, Волшебник + base_stats, starting_hp, hit_die, actions, bonus_actions.
- leveling.json: пороги XP для автоматического повышения уровня.
Путь к правилам задаётся через RULES_DIR (в Docker — /configs/rules).

Схема действия (в actions_json и bonus_actions_json):
{name, attack_bonus, damage_formula}
Пока поддерживаются только атакующие действия.

3.2. Кубики и модификатор характеристики
- Формат формул: XdY, XdY+Z, XdY-Z, dY. Ограничения: 1 ≤ X ≤ 100, 2 ≤ Y ≤ 1000, |Z| ≤ 1000.
- Modifier(score) = (score - 10) >> 1 (арифметический сдвиг, округление вниз — как в правилах D&D).
- Критическое попадание удваивает количество кубиков урона (бонус не меняется).

3.3. Сценарий боя (Combat Flow)
1. Формирование боя: Мастер через REST API выбирает монстров из бестиария (с автогенерацией копий: «Гоблин #1», «Гоблин #2») и отмечает присутствующих игроков.
2. Бросок инициативы:
   - Последовательный расчёт 1d20 + Modifier(DEX) для каждой сущности.
   - Разрешение ничьих: больший Modifier(DEX) выше. При полном равенстве — игрок ходит раньше монстра.
   - Финальный детерминирующий ключ — display_name.
3. Ход участника:
   - 1 основное действие + 1 бонусное действие.
   - Атака: 1d20 + attack_bonus vs AC. Натуральная 1 — промах, натуральная 20 — попадание и крит (кубики урона ×2).
   - Формула урона — из actions_json атакующего.
   - Переход хода — по явной команде.
4. Условия падения (HP = 0):
   - Монстр получает статус dead и пропускается.
   - Персонаж игрока получает статус unconscious, пропускает ходы до конца боя.
   - После боя HP всех игроков восстанавливается до максимума.
5. Финал боя и XP:
   - Мастер вызывает POST /finish.
   - Суммарный XP всех убитых монстров начисляется полностью каждому игроку (решение отличается от официальных правил D&D — см. раздел 6).
   - Проверка порога из leveling.json → автоматическое повышение уровня.
   - Рост HP на уровне: max(1, hit_die/2 + 1 + Modifier(CON)).

4. Архитектура событий (Event Bus и polling)
Event Bus — ядро real-time. SSE не используется; вместо него Redis event buffer и polling со стороны клиента.

[ Игрок (TG) / Мастер (REST/Swagger) ]
         |
         v
[ REST / TG Controller ]
         |
         v
[ Combat Engine Logic ] --(запись)--> [ PostgreSQL (SSOT) ]
         |
         v
[ Event Bus (chan Event) ]
         |---> [ DB Log Subscriber ]         -> dice_rolls_log
         |---> [ Redis Event Buffer ]        -> encounter:<id>:events (list, TTL 24h)
         |---> [ TG Notification Publisher ] -> чаты игроков

Правила:
- События публикуются только после успешного commit транзакции.
- Подписчики регистрируются один раз при старте и сами фильтруют по encounter_id.
- Буфер канала подписчика — 256; при переполнении пишется предупреждение в лог (остаток проблемы — TD-23).
- Close() закрывает каналы подписчиков; run() дожидается их завершения через sync.WaitGroup.

Как работает polling:
1. Каждое игровое действие → Event → Event Bus.
2. Redis Event Buffer Subscriber выполняет RPUSH encounter:<id>:events <json> и EXPIRE ... 86400 в одном pipeline.
3. Мастер периодически (раз в 1–2 секунды) вызывает:
   GET /api/v1/encounters/:id/events?after=<index>
4. Сервер выполняет LRANGE encounter:<id>:events <index> -1, возвращает массив новых событий и next_index.
5. Если клиент пришёл с after больше текущей длины списка (истёк TTL), возвращается next_index = LLEN без ошибки.
6. Клиент (Swagger UI, Postman, скрипт) обновляет локальный индекс и повторяет запрос.
TTL списка — 24 часа от последнего события.

Преимущества перед SSE:
- Проще в отладке (curl возвращает результат, а не висит).
- Не требует http.Flusher и долгоживущих соединений.
- Работает через любой прокси.
- Задержка 1–2 секунды не критична для пошагового боя.

6. Решения, отличающиеся от официальных правил D&D 5e
Зафиксированы осознанно:
- XP: суммарный XP убитых монстров начисляется полностью каждому игроку. По официальным правилам XP делится между участниками.
- Стартовые HP: берутся из classes.json без учёта расового бонуса к CON (упрощение).
- AC: 10 + Modifier(DEX) (без брони и щитов).
Всё остальное (попадание ≥ AC, натуральные 1 и 20, крит удваивает кубики урона, рост HP на уровне, пороги XP) — официальные правила.


Дорожная карта разработки (Sprint Roadmap)
Версия 2.3. Основание: редакция v2.2 с правками по итогам Спринтов 2–5 и TECH_DEBT.

Общие соглашения, действующие во всех спринтах.
- Команды выполняются из корня проекта в PowerShell 7. Алиас для Compose:

  function dc { docker compose -f deploy/docker-compose.yml --env-file .env @args }

- SQL: dc exec postgres psql -U go_dnd_user -d go_dnd -c "...".
- HTTP: curl.exe (не curl); JSON — снаружи одинарные кавычки, внутри двойные.
- Миграции лежат в internal/migrations/sql/. Нумерация:
  000001 — users;
  000002 — уникальные частичные индексы;
  000003 — tables, table_members;
  000004 — characters, bestiary_templates;
  000005 — encounters, encounter_entities, dice_rolls_log.
- Слои: usecase знает только интерфейсы (репозитории, нотификатор). Интерфейс объявляется там, где используется. transport маппит доменные ошибки в HTTP-коды. Ответы с кодом ≥ 500 логируются с request_id.
- Пустые списки в JSON отдаём как [], а не null (make([]T, 0)).
- Каждая задача — отдельный коммит. В конце спринта go vet ./... && go test ./... зелёные.

Спринт 4. Боевой движок, Event Bus, polling, XP
Длительность: 2 недели.
Фокус: боевой цикл, real-time события через polling, начисление опыта.

Что изменилось относительно v2.2.
Архитектурные решения (отличаются от ТЗ; при несогласии поправить до начала спринта):
- PostgreSQL — единственный источник истины для состояния боя: раунд, текущий ход, порядок очереди и экономика действий хранятся в БД (колонки), а не в Redis. Причина: ТЗ требует SSOT и транзакции (TD-04); состояние из двух хранилищ нельзя обновить атомарно. Redis в MVP — только буфер событий для polling. Кэш очереди в Redis отложен (TD-24).
- Снимок при создании боя: в encounter_entities копируется в том числе xp_reward. Иначе правка или удаление шаблона монстра после спавна ломает подсчёт XP.
- Статус сущности (active / unconscious / dead) хранится явно (TD-06).
- Event Bus с глобальными подписчиками: три подписчика регистрируются один раз при старте и сами фильтруют по encounter_id. События публикуются только после успешного commit.
- Финал боя не удаляет Redis-ключи событий. Ключи живут по TTL, который продлевается на каждом событии (TD-16).
- Нужны ход и атака от имени игрока из Telegram: новая Task 4.9.
- Порядок задач изменён: polling теперь 4.6, после боевого цикла, чтобы проверять его на реальном бою.
Правила D&D (официальные, раз в ТЗ не менялись): попадание, если бросок ≥ AC; натуральная 1 — промах; натуральная 20 — попадание и крит (кубики урона ×2); рост HP на уровне — среднее значение кубика + модификатор CON.
Исправления ошибок v2.2: модификатор DEX через Modifier (не /2); HP игроков восстанавливаются после боя всем, а не только при Level Up (TD-01); явный ключ сортировки инициативы (TD-03); транзакции (TD-04); идемпотентный /finish (TD-05).

Task 4.5. Боевой цикл: атака, HP, смена хода

$i = 0
while ($true) {
  r=curl.exe-s"http://localhost:8080/api/v1/encounters/id/events?after=$i" `

  $i = $r.next_index
  Start-Sleep -Seconds 1
}
Пока цикл работает, выполнять атаки: события появляются по одному, без повторов.

Спринт 4. Боевой движок, Event Bus, polling, XP
Длительность: 2 недели.
Фокус: боевой цикл, real-time события через polling, начисление опыта.

Что изменилось относительно v2.2.
Архитектурные решения (отличаются от ТЗ; при несогласии поправить до начала спринта):
- PostgreSQL — единственный источник истины для состояния боя: раунд, текущий ход, порядок очереди и экономика действий хранятся в БД (колонки), а не в Redis. Причина: ТЗ требует SSOT и транзакции (TD-04); состояние из двух хранилищ нельзя обновить атомарно. Redis в MVP — только буфер событий для polling. Кэш очереди в Redis отложен (TD-24).
- Снимок при создании боя: в encounter_entities копируется в том числе xp_reward. Иначе правка или удаление шаблона монстра после спавна ломает подсчёт XP.
- Статус сущности (active / unconscious / dead) хранится явно (TD-06).
- Event Bus с глобальными подписчиками: три подписчика регистрируются один раз при старте и сами фильтруют по encounter_id. События публикуются только после успешного commit.
- Финал боя не удаляет Redis-ключи событий. Ключи живут по TTL, который продлевается на каждом событии (TD-16).
- Нужны ход и атака от имени игрока из Telegram: новая Task 4.9.
- Порядок задач изменён: polling теперь 4.6, после боевого цикла, чтобы проверять его на реальном бою.
Правила D&D (официальные, раз в ТЗ не менялись): попадание, если бросок ≥ AC; натуральная 1 — промах; натуральная 20 — попадание и крит (кубики урона ×2); рост HP на уровне — среднее значение кубика + модификатор CON.
Исправления ошибок v2.2: модификатор DEX через Modifier (не /2); HP игроков восстанавливаются после боя всем, а не только при Level Up (TD-01); явный ключ сортировки инициативы (TD-03); транзакции (TD-04); идемпотентный /finish (TD-05).

Task 4.5. Боевой цикл: атака, HP, смена хода
Пошаговый план:
1. POST /api/v1/encounters/{id}/actions/attack, тело {"actor_id","target_id","action_name"}. Сигнатура usecase: Attack(ctx, requester Identity, encounterID, req), где Identity{UserID, Role}. Мастер действует за любую сущность своего стола; игрок (Task 4.9) только за свою: characters.player_id == requester.UserID, иначе 403.
2. Транзакция с блокировкой строки боя (FOR UPDATE): все действия одного боя выполняются последовательно.
3. Проверки: бой active (409); актёр и цель принадлежат бою (404); actor.turn_position == encounters.current_turn и актёр active (409 «не ход этой сущности»); цель не dead; цель ≠ актёр (400).
4. Действие ищется по action_name сначала в actions_json (тратит Action), затем в bonus_actions_json (тратит Bonus Action). Не найдено → 400; слот уже использован → 409.
5. Бросок: d20; натуральная 1 — промах; натуральная 20 — попадание и крит; иначе d20 + attack_bonus ≥ target.ac — попадание. При попадании урон Roll(damage_formula) (при крите .Crit()); hp = max(0, hp − урон).
6. hp == 0: монстр → dead, игрок → unconscious. Поставить флаг использованного слота, commit.
7. После commit: DiceRoll (атака), DiceRoll (урон, если попал), Damage{target, damage, hp_left, status, all_monsters_dead}.
8. POST /api/v1/encounters/{id}/turn/end (Мастер; игрок — Task 4.9): та же блокировка; найти следующую сущность по turn_position со статусом active, пропуская dead и unconscious; при переходе через конец очереди round++; если активных нет → 409 «нет активных участников, завершите бой». Обнулить action_used и bonus_action_used у той, чей ход начинается. После commit: TurnChange{round, entity}.
9. Тесты usecase с mock-репозиторием и фиксированными кубиками: промах, попадание, крит, смерть монстра, потеря сознания игрока, пропуск хода мёртвого, повторное использование Action (409), чужой ход (409).
Как проверить: провести раунд через curl.exe. HP цели уменьшилось; броски в dice_rolls_log; мёртвый монстр пропускается; после круга round вырос.

Task 4.6. Redis Event Buffer + polling-эндпоинт
Пошаговый план:
1. go get github.com/redis/go-redis/v9; подключение в run() с Ping; закрытие при остановке.
2. subscribers/redis_buffer.go: для каждого события сериализовать JSON {"type","encounter_id","payload","created_at"} и в одном pipeline выполнить RPUSH encounter:<id>:events <json> и EXPIRE encounter:<id>:events 86400. TTL продлевается на каждом событии. Ошибки Redis логируются, подписчик продолжает работу.
3. GET /api/v1/encounters/{id}/events?after=<index> (JWT Мастера, бой принадлежит его столу иначе 404). after — целое ≥ 0 (по умолчанию 0), иначе 400.
4. LRANGE encounter:<id>:events <after> -1. Ответ: {"events": [...], "next_index": after + len(events)}. Если список истёк по TTL и клиент пришёл с after, который больше длины списка, вернуть next_index = LLEN.
5. Тесты: подписчик и хендлер против miniredis (github.com/alicebob/miniredis/v2) или mock-интерфейса; проверить after=0, after=N, пустой результат.
Как проверить: запустить цикл опроса (PowerShell):
$i = 0
while ($true) {
  r=curl.exe-s"http://localhost:8080/api/v1/encounters/id/events?after=$i" `
    -H "Authorization: Bearer $token" | ConvertFrom-Json
  $r.events | ForEach-Object { $_ | ConvertTo-Json -Compress -Depth 5 }
  $i = $r.next_index
  Start-Sleep -Seconds 1
}
Пока цикл работает, выполнять атаки: события появляются по одному, без повторов.

Task 4.8. Финал боя и XP
Пошаговый план:
1. POST /api/v1/encounters/{id}/finish (Мастер-владелец).
2. Идемпотентность (TD-05) атомарным UPDATE, а не «прочитал статус, потом записал»: UPDATE encounters SET status='finished', finished_at=now() WHERE id=$1 AND status='active'. Затронуто 0 строк → 409. Начисление XP выполняется только после успешного UPDATE.
3. Всё в одной транзакции: totalXP = SUM(xp_reward) сущностей monster со status='dead' из снимка в encounter_entities; для каждого игрока боя (включая потерявших сознание): xp += totalXP (полностью, по ТЗ); newLevel = rules.LevelForXP(xp); за каждый полученный уровень max_hp += max(1, hit_die/2 + 1 + Modifier(CON)); всем игрокам боя: current_hp = max_hp (TD-01), независимо от Level Up.
4. Redis-ключи событий не удалять (см. решение выше).
5. После commit: EncounterFinish{total_xp, players: [{name, xp_gained, level_before, level_after, hp}]}.
6. Тесты usecase: XP из снимка при удалённом шаблоне; повторный вызов → 409 и XP не удваивается; повышение сразу на два уровня; восстановление HP игроку без Level Up; потерявший сознание игрок тоже получает XP.
Как проверить: бой на 300 XP (2 гоблина по 150). После /finish каждому игроку +300 XP, уровень растёт при достижении порога, current_hp = max_hp. Второй /finish → 409, XP не изменился. В polling пришёл EncounterFinish.

Task 4.9. Telegram — ход игрока кнопками
Что делаем: игрок управляет своим ходом из Telegram.
Пошаговый план:
1. Когда наступает ход игрока (TurnChange), сообщение из Task 4.7 идёт с кнопками «Атаковать» и «Закончить ход».
2. Цепочка callback (индексы вместо имён, чтобы уложиться в лимит callback_data 64 байта): atk:<encounter_id> → показать действия персонажа (act:<encounter_id>:<action_idx>; бонусные действия — в конце списка); act:<encounter_id>:<action_idx> → показать живые цели (tgt:<encounter_id>:<action_idx>:<turn_position>); tgt:... → вызвать Attack с Identity{UserID: игрок, Role: player}; end:<encounter_id> → EndTurn от игрока.
3. Игрок определяется по telegram_id. Сервер проверяет всё сам: чей ход, чей актёр, какой слот свободен. Данным из callback_data не доверяем.
4. После действия сообщение редактируется (результат атаки); общие уведомления всем игрокам идут через обычный Publisher.
5. Ошибки usecase (не твой ход, слот занят) — AnswerCallbackQuery с понятным текстом.
Как проверить: бой с одним игроком и одним монстром. Игрок атакует и завершает ход кнопками; попытка нажать «Атаковать» вне своего хода даёт alert; Мастер видит все события в polling.

Решения, отличающиеся от официальных правил D&D 5e.
Зафиксированы осознанно; при желании можно изменить.
- XP: суммарный XP убитых монстров начисляется полностью каждому игроку (по ТЗ). По официальным правилам XP делится между участниками.
- Стартовые HP: берутся из classes.json без учёта расового бонуса к CON (упрощение).
- AC: 10 + модификатор DEX (без брони и щитов).
- Всё остальное (попадание ≥ AC, натуральные 1 и 20, крит удваивает кубики урона, рост HP на уровне, пороги XP) — официальные правила.
